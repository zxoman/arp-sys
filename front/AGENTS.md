# figma-make-app

React + Vite + Tailwind CSS project running inside Figma Make.

## Development Server

A Vite development server is **already running** on `$PORT` (default 8443). You don't need to start it manually.

- Preview URL: The user can access the running app through the preview panel
- Hot reload: Changes to source files are reflected immediately

## Project Structure

This is the canonical project structure. Start with task-relevant files below. Only follow imports or inspect other files when required, when a documented path is missing, or when the repository contradicts this guide.

- `src/main.tsx` - React entrypoint; imports `src/index.css` and mounts `src/App.tsx` into the `#root` element
- `src/App.tsx` - Primary application component and the usual starting point for UI work
- `src/index.css` - Global CSS entrypoint and Tailwind CSS v4 import
- `index.html` - Vite HTML shell containing the `#root` element and loading `src/main.tsx`
- `package.json` - Project dependencies and the Vite build, development, preview, and formatting scripts
- `vite.config.ts` - Vite configuration with React, Tailwind CSS v4, and Figma Make plugins plus the `@` alias for `src`
- `.mise.toml` - Toolchain versions for Node.js and pnpm
- `src/lib/api.ts` - Fetch client for the Laravel API (`backend/`); base URL from `VITE_API_URL`, otherwise `/api/v1` in dev (proxied by Vite to `http://127.0.0.1:8000`) or `http://localhost:8000/api/v1` in a build; Sanctum token from `?token=` or localStorage

## API Integration

The prototype stores its demo data in localStorage, but the **buildings, units, clients, reservations, contracts, receipts and rent-due pages — plus the wired report tabs and the header bell — are fully server-driven**:

- **Login:** there is one login screen for the whole app (`src/screens/Login.tsx`) and it is the API session. It posts to `POST /auth/login`, stores the Sanctum token in `localStorage` (`aqar.api.token`) and the gate in `App.tsx` only mounts the shell once `/auth/me` has confirmed it; «خروج» in a page header calls `POST /auth/logout` and returns to the same screen. No page owns its own login form.
- A token can also be passed in the URL as `http://localhost:8443/?token=<sanctum-token>` (query before the `#`); it is moved into `localStorage` and removed from the URL.
- `GET /admin/buildings` powers the table: search, sort and pagination are **server-side** (`search`, `sort`, `dir`, `page`, `per_page`), passed through `DataTable`'s `serverSearch` / `serverSort` / `serverPagination` props. Arabic type/activity labels are searched too (`برج` → tower, `سكني` → residential).
- `POST/PUT/DELETE /admin/buildings` drives the add/edit/delete drawer. `src/lib/api.ts` maps the Arabic labels to the API enums (`building | tower | house | office_building`, `residential | administrative | commercial | medical | hotel`).
- **Units** (`src/screens/movement/Units.tsx`) reuse the same app session and `DataTable` server props against `GET /admin/units`: `search`, `sort` (`id | name | type | purpose | area | status`), `page`, `per_page`, plus the `building_id`, `floor_id`, `type`, `purpose` (`sale | rent | both`) and `sellable` / `status` filters. The «غير قابلة للبيع» filter sends `sellable=0`; the other states send `status=`.
- The unit drawer posts the API's four types only (`apartment | shop | warehouse | studio`; the prototype's روف / مكتب / ميزانين / بدروم have no model yet). The API requires `activity` when a building has more than one, so the form shows the picker only then (and fills it automatically otherwise). `building_id` is immutable after creation.
- Sale price = `area × price_per_meter` unless the user edits it (then `sale_price` overrides it and the hint offers «إعادة الحساب»); rent-only units send `price_per_meter`/`sale_price` as `null` and show «—» in the price column — the rent amount is entered at contract time. There is no monthly rent or description field on units.
- «غير قابلة للبيع» is a manual flag with a required reason, shown as a red chip plus a caption under the unit name; purpose, sale fields and the flag are locked once the API reports `sold` or `rented` (those statuses come only from reservations and contracts).
- **Clients** (`src/screens/movement/Clients.tsx`) use the same gate/table pattern against `GET /admin/clients` (`search`, `sort` = `id | name | phone | phone_2 | national_id | created_at`, `page`, `per_page`) plus `POST/PUT/DELETE /admin/clients`. The drawer mirrors the API model only: name (required), phone, phone_2, national_id, notes — the prototype's client type (مشتري / مستأجر / مالك), address and email have no API fields, and the drawer says so.
- Phone validation on the client form accepts `01xxxxxxxxx`, `+201xxxxxxxxx` and Arabic-Indic digits (the API normalizes both numbers to `+20…`). A duplicate number never blocks the save: `meta.duplicate_phone` / `meta.duplicate_client_id` becomes a warning toast naming the other client's code. Delete asks for confirmation and surfaces the API's 422 guard (active reservation or any contract, even cancelled).
- A 401/419 anywhere drops the token (`clearToken()`), which the auth provider turns into a signed-out app: the login screen comes back with «انتهت الجلسة، سجّل الدخول من جديد.»; other failures show a retry banner. 422 responses are mapped back onto the form fields.
- **Reservations** (`src/screens/movement/Reservations.tsx`) use the same gate/table pattern against `GET /admin/reservations` (`search` = client/unit/building name, `status` = `active | converted | cancelled`, `page`, `sort` = `id | reservation_date | status`, `per_page`) plus `POST /admin/reservations`, `POST /admin/reservations/{id}/cancel` and `GET|POST /admin/reservations/{id}/payments` (+ `POST …/payments/{payment}/cancel`). Status chips map to `status=` (`نشط` → `active`, `محوّل لعقد` → `converted`, `ملغي` → `cancelled`); the prototype's «منتهي» has no API status and is not shown.
- A reservation carries **no price**: the drawer asks for client, unit **or** building (building-level reservations have no unit), date and an optional first payment; `deposit_paid` is the sum of the valid payments and the agreed price is entered on the contract. Choosing a unit disables and clears the building picker, and vice versa.
- The unit picker only offers units the API reports `available` and sellable (`status=available&sellable=1`); a reservation turns the unit «محجوزة» and cancelling it returns it to «متاحة». The details drawer lists the payments with add/cancel (both cancellations require a reason) and shows `unit_type` through `unitTypeLabel()` (`apartment` → شقة).
- Convert-to-contract is intentionally **not** wired yet: the sale form's «حجز جديد» links to this page to create a reservation first (a lease can skip the reservation and pick client + unit directly). The old demo `ReservationFormDrawer` export here is now unused dead code (kept, not imported).
- **Contracts** (`src/screens/movement/Contracts.tsx`) use the same gate/table pattern against `GET /admin/contracts` (`search` = number/client/unit/building, `type` = `sale | rent`, `status` = `draft,active,cancelled`, `page`, `sort` = `id | number | type | contract_date | total_price | status`, `per_page`) plus `POST /admin/contracts`, `POST /admin/contracts/{id}/post`, `POST /admin/contracts/{id}/cancel` and `GET /admin/contracts/{id}`. The type chips read their counts from `meta.counts` (`all` / `sale` / `rent`), which the API computes **before** the `type` filter — the table is server-filtered, so the client cannot count them from the rows.
- A **sale** contract is created from an **active API reservation** (client, unit and unit type come from it; «حجز جديد» jumps to the reservations page). A **lease** can start from a reservation too, but it no longer has to: the lease form shows «الحجز (اختياري)» plus «العميل» and «الوحدة» pickers (`fetchAllClients()` + `fetchReservableUnits()` filtered to `purpose !== 'sale'`, both loaded on the first switch to «إيجار»). Picking a reservation fills them and locks them; clearing it clears and unlocks them, and a direct lease is posted with `reservation_id: null`. The picked unit is re-read with `GET /admin/units/{id}` to prefill the sale price and to block an unsuitable unit (`is_sellable=false`, or `purpose` says sale-only for a lease and vice versa); that unit is kept in the picker's own list even when a reservation has already taken it off the «متاحة» list.
- Sale: `total_price` (unit price), `discount` + `discount_reason` (company discount; the API stores `total_price` as the **net** amount and keeps the discount next to it), `agreed_down_payment`, then a free `schedule[]`. The screen only *warns* when the schedule total ≠ price − down payment; the API accepts any schedule.
- Rent: `monthly_rent`, `duration_months`, `start_date`, `end_date` (computed: start + duration − 1 day), `security_deposit`, `advance_months`, `annual_increase_pct`, `increase_from_year`, and `total_price` = rent over the whole term with the yearly increase applied. «توزيع» builds an advance row (rent × advance months, due on the contract date) plus one row per interval; a lease posted without a schedule gets one row per month instead.
- **Draft or posted in one step:** «حفظ كمسودة» sends `status=draft` (the free schedule is kept in `draft_schedule` and the unit/reservation are untouched); «ترحيل العقد» sends `status=active`, and a draft can be posted later from the row («ترحيل») or the details view (`POST …/post`), which creates the installments, converts the reservation and sets the unit `sold` / `rented`.
- The details view (`GET /admin/contracts/{id}`) shows client/unit, the financial stats (discount, down payment, installments total, paid, remaining — remaining is «—» once the contract is cancelled), the draft schedule or the installments (status chip shows «متأخر» when `is_overdue`), printing and cancel-with-reason. Renewal/return/receipt actions were dropped here: those screens still run on demo data. Cancelling a draft only cancels the draft; cancelling an active contract cancels its installments (they stay, marked «ملغي») and frees the unit.
- Printing reuses the demo `ContractDoc` through `contractFromApi` / `clientFromApi` / `scheduleOf`, so the printed document stays one component for local and server contracts.
- **Receipts** (`src/screens/movement/Receipts.tsx`) are the collection page: one receipt (إيصال قبض) covers **several installments** of one contract and/or **part of its down payment** (مقدم/تأمين), with one number, total, date, method and reference. It reads `GET /admin/receipts` (`search` = receipt number, contract number, client/phone, unit or building; `status` = `valid | cancelled`; `page`, `sort` = `number | paid_at | total_amount | status`, `per_page`) and posts to `POST /admin/receipts`, `POST /admin/receipts/{id}/cancel`; `GET /admin/receipts/{id}` is re-read for the details panel. The picker lists **active** contracts only (`fetchActiveContracts()` via `status=active`), because a draft has no installments and a cancelled schedule is closed.
- The form loads the picked contract with `GET /admin/contracts/{id}` and lists every row with something still owed — a «مقدم» row from `remaining_down_payment` first (it stays first, with the paid/remaining columns, until the down payment is fully collected), then the installments by `sequence_number`. Each row carries a «المدفوع الآن» input: typing there sets that line alone (capped at what it still owes, Arabic-Indic digits accepted, a «سابقًا …» caption shows what was already paid) and `المبلغ المستلم` is rebuilt as the sum, so total and lines can never disagree. Ticking a row fills it at its remaining amount. Typing in `المبلغ المستلم` instead distributes over the **ticked** rows first, in table order, each up to what it still owes, then continues into the rows after them; every row the amount does not reach is dropped again (never sent with 0), so a *partial* amount on one row, on «حدّد الكل», or more than the ticked rows can take all work and the leftover of each row stays in the table for the next receipt. Nothing is auto-split on the server: the client sends `installments: [{ installment_id, amount }]` (positive lines only) plus an optional `down_payment`, and the API validates each line against its own remaining balance; 422 field messages are mapped back onto «المبلغ المستلم» (never Laravel's «… (and 1 more error)» summary), and an amount above what is available says so with the available figure.
- `PAYMENT_METHODS` / `PAYMENT_METHOD_TO_API` / `PAYMENT_METHOD_FROM_API` in `src/lib/api.ts` mirror the API enum: نقدي · تحويل بنكي · شيك · فودافون كاش · إنستاباي · أخرى (`cash | bank_transfer | cheque | vodafone_cash | instapay | other`).
- Saving shows a toast with a «طباعة» action that prints the saved receipt (number, client, contract, covered lines, method, reference, amount) through `ReceiptDoc`; the amount input is remounted (`formEpoch`) after a save because `NumericInput` keeps its own text until remounted. The history table mirrors the API's search/sort/paging, `FilterChips` «الكل / صالح / ملغي», a details panel (`RecordView`) with the covered lines and the creator, print, and cancel-with-reason: the cancellation is confirmed, then a modal asks for the reason and warns that every line is reversed (nothing is deleted) and that the installments return to what they were.
- The demo handoff `RECEIPT_PREFILL_KEY` (from «تسجيل دفع» on the rent-due page — now the server-driven collection page — the installments report and global search) is honoured **only** when the id is numeric and names an active API contract/installment; otherwise the form opens empty. The collection page hands over the contract id plus, for an installment row, the installment id, so the receipt form opens with that line already filled.
- **Rent due / collection** (`src/screens/movement/RentDue.tsx`) is read-only and reads `GET /admin/installments` and `GET /admin/down-payments` (tabs «الأقساط» / «المقدمات»), plus `GET /admin/{installments|down-payments}/calendar?month=YYYY-MM` for the month grid. Both lists take `search` (contract number, client name/phone, unit, building), `type` = `sale | rent`, `status` = `due | overdue | partially_paid | paid`, `due_on` (the calendar day), `page`, `sort`, `dir`, `per_page`.
- The status shown is the API's display state recomputed against **today**, not the stored `installments.status`: `overdue` wins over `partially_paid`, so the chips partition every row. The type chips read `meta.type_counts` (counted before the `type` filter) and the status chips read `meta.counts` (after the type filter, before status/day), so selecting a chip never rewrites its own numbers. The three cards («إجمالي المستحق / المحصل / المتأخر») are `meta.totals` for the current search/type scope, not the visible page.
- The calendar shows «مدفوع / قادم / متأخر» per day from the server rollup (`total`, `overdue`, `due`, `paid`); clicking a day filters the table through `due_on` and a removable «يوم …» chip clears it. The «المقدمات» tab shows one row per active contract (sequence 0, labelled «مقدم») due on the contract date; its money is collected through the receipts page like any other row, so every «تسجيل دفع» button does `goToReceipt(contractId, installmentId?)`.
- **Header bell** (`useNotices` in `src/Shell.tsx`) fetches `GET /admin/notifications`: two groups, overdue and due-today, of unpaid installments/rents on active contracts. Each group header shows the server's full `total` while the popover lists at most 10 rows (the API caps them); opening the bell still marks the loaded keys as seen locally. It refreshes on `focus`, `hashchange`, `aqar:token-changed` (dispatched by `setToken` / `clearToken`) and every 120 s, and skips the request entirely without a token. Lease-expiry and maintenance alerts were dropped from it — maintenance has no API and expiry was not requested.
- **Installments summary report** (`src/screens/reports/ReportInstallments.tsx`, first tab «ملخص الأقساط والعقود») is server-driven through `GET /admin/reports/installments-summary` (`fetchInstallmentsSummary`). Its own filters are the type chips (counts from `meta.counts`, counted before the `type` filter), «المبنى» (`fetchAllBuildings()`), «العميل / المستأجر» (`fetchAllClients()`) and «حالة العقد» limited to «نشط / ملغي» — the prototype's مكتمل/منتهي/مجدد/مرتجع have no API state. Drafts are never listed (a draft has no schedule).
- Each row is one contract: sale shows «سعر الوحدة / المقدم / باقي المقدم / إجمالي الأقساط / الأقساط المسددة / آخر قسط مسدد / القسط الحالي المطلوب سداده / متبقي القسط الشغال / إجمالي المتبقي»; lease shows «الإيجار الشهري / التأمين / تاريخ البداية / تاريخ النهاية» with the same installment columns. The KPI cards, the donut and the Excel/print actions are computed from the returned rows (whole result set — the report is not paged, it is searched/sorted/exported client-side). The card computes with `remaining <= 0` meaning collected; the API sends `last_paid_installment` / `next_due_installment` as `{sequence_number, due_date}`.
- Its `SummaryRow` is a plain row shape (`InstallmentRef` = `{seq, dueDate}`) filled either by `summaryRowFromApi` or by the demo `useSummaryRows`, so the demo rows keep working next to the API ones.
- **Due & overdue report** (second tab «الأقساط المستحقة والمتأخرة»، `screen: report-due-overdue`) reads `GET /admin/reports/due-overdue` (`fetchDueOverdueReport`): unpaid installments of active contracts that are due today or late. Its filters are «المبنى» / «العميل» (loaded from the API) and the delay chips «الكل / 0-30 / 31-60 / 61-90 / +90 يوم», whose `(n)` counts come from `meta.buckets` — counted over the whole scope, so a chip only narrows the table. The cards are `meta.buckets[selected]` («إجمالي المستحق والمتأخر»), `meta.buckets['90+']`, the distinct clients of the visible rows («عملاء متأخرون») and `meta.due_within_7_days` («يستحق خلال 7 أيام», a separate figure, not a bucket); the donut is the four bucket totals.
- A row opens the shared record panel built with `compose()` from `src/screens/records.tsx` (exported for reuse) — contract/client/unit, the delay bucket and the due numbers, printing and CSV included — plus a «تسجيل دفع» button that hands the contract + installment to the receipts form through `goToReceipt(contractId, installmentId)`. The table is not paged: it is searched/sorted/exported client-side.
- **Customer statement** (`src/screens/reports/ReportClientStatement.tsx`, `screen: report-client-statement`) is the only client report: «تقرير العملاء» was deleted because its مشتري/مستأجر/مالك split (and the owner-share table) has no API field. It reads `GET /admin/reports/customer-statement` (`fetchCustomerStatement`) for the picked client (`fetchAllClients()`) over the client's **whole history** (`STATEMENT_ALL_TIME_FROM`/`TO`), then filters «من / إلى تاريخ» and the contract picker locally — asking the API for a period would start the running balance from zero. The «العقود» table under the ledger is the API's per-contract rollup (value, down payment paid/left, installments total, paid rows, next due, overdue, remaining, status), and its contract picker is that list.
- Each movement is a row: the contract's `agreed_down_payment` (dated on the contract) and every non-cancelled installment `amount` debit; every valid payment credits (a reservation payment is labelled «دفعة حجز» and has no contract). The closing balance is the last balance up to «إلى تاريخ» (carried forward, not just the shown rows); the contract filter rebuilds the balance for that contract alone; «متأخرات» is the sum of `installment_totals.overdue` of the shown contracts. Cancelled payments are excluded from the balance and named in a footnote.
- **Building & unit statements** (`src/screens/reports/ReportStatements.tsx`, `screen: report-building-statement` / `report-unit-statement`) are server-driven: «كشف عقار» reads `GET /admin/reports/building-statement` (`fetchBuildingStatement`) for the building picked from `fetchAllBuildings()` (the first building is selected automatically), and «كشف وحدة» reads `GET /admin/reports/unit-statement` (`fetchUnitStatement`) for the unit clicked on the building figure, fed by `fetchAllUnits(buildingId)`. Both ask for the whole history (`STATEMENT_ALL_TIME_FROM`/`TO`) because the screens have no date pickers, and use the real calendar (`toISO(new Date())`), never the demo `TODAY_ISO`.
- The building view shows the building header (code, floors, units, «حتى» today), the five unit-count cards (including «الوحدات المغلقة» = `counts.closed`, i.e. available but «غير قابلة للبيع»), the financial totals table over **active contracts only**, the floor figure (clicking a floor replaces the hint with its six money tiles plus its units), the contracts table (type/unit/client/date/value/paid/remaining/due/overdue/status) and, only when non-empty, the reservations table (a building-level reservation shows «حجز على العقار»). When the API reports `totals.cancelled > 0` a footnote says cancelled payments do not count.
- The unit view shows the building figure in unit mode, then the unit header (status via `is_sellable`, floor, area, rooms/bathrooms from `units.rooms/bathrooms`, purpose, sale price), six figures (contract card + sales/remaining/due/monthly rent/overdue/deposit), a message when the unit has neither an active contract nor an open reservation, the reservation card while the unit is only reserved, the client card and the contract card (lease terms + «حالة الإيجار» مسدد/متأخر/متهرب with `ABSCOND_MONTHS = 3`, or sale price/down payment paid and left), and the schedule table (state مدفوع/جزئي/متأخر/قادم/ملغي, plus «يوم السداد» = `paid_at`). «حالة الإيجار» stays client-side logic recomputed from the server's `is_overdue` rows.
- The two statements drop the demo-only columns that have no API source: maintenance/profit, client type/address, a unit monthly rent and a reservation expiry.
- **Unit status** (`src/screens/reports/ReportUnits.tsx`, tab «حالة الوحدات»، `screen: report-unit-status`) is server-driven through `GET /admin/reports/unit-status` (`fetchUnitStatus`); the other six tabs of that screen (متاحة/محجوزة/مباعة/مؤجرة/مرتجعة/غير قابلة للبيع) still run on demo data and keep the demo filter bar, while the status tab brings its own.
- Its filters are «المبنى» (`fetchAllBuildings()`), «نوع الوحدة» (only the API's `apartment | shop | warehouse | studio`, via `UNIT_TYPE_TO_API`) and «الغرض» (`sale | rent | both` via `PURPOSE_TO_API`); the demo floor filter is dropped because the report has no floor source in this mode.
- Eight cards: `counts.total` (with the area), one per state (`available` / `reserved` / `sold` / `rented` / `closed` = «غير قابلة للبيع») showing the count, its share and the money behind it (sale value, or the live monthly rent for rented), then `totals.sale_value` with the price per m² and `totals.monthly_rent`. The donut is the five counts and the per-building table is `by_building` (five counts with their percentages, sale value, monthly rent, area).
- The units table lists building, number, type, floor, area, purpose, sale price, monthly rent and the state; a closed unit shows its flag reason under the chip. A footnote says closed units are counted apart and that there is no «مرتجعة» state (a cancelled contract returns the unit to «متاحة»). Error banner and real today as in the other wired reports.
- **Monthly revenue** (`src/screens/reports/ReportInstallments.tsx`, fourth tab «الإيرادات الشهرية»، `screen: report-monthly-revenue`) reads `GET /admin/reports/monthly-revenue` (`fetchMonthlyRevenue`). It has no date pickers: it asks for the last 12 calendar months up to the real today (`lastMonths(12, toISO(new Date()))`, from the 1st of the first month to the last day of the last one) and offers only the «المبنى» filter (`fetchAllBuildings()`).
- The report is **money collected**, not contract values: one row per month with payment lines, distinct receipts, «دفعات الحجز / مقدمات وتأمينات / أقساط وإيجارات», the total and the running total. The «ملغي (لا يُحتسب)» column appears only when the period has cancellations, and a footnote says cancelled money is dated by its cancellation month and does not enter the revenue. A second footnote explains why receipts < lines (a reservation deposit or a payment recorded straight on an installment has no receipt; its money is still counted). Cards: period total (with line/receipt counts), the current month, the monthly average and the best month; charts are the monthly bars and the last-6-months cumulative area.
- **Daily collection** (fifth tab «التحصيل اليومي»، `screen: report-daily-collection`) reads `GET /admin/reports/daily-collection` (`fetchDailyCollection`) for «المبنى» + «من / إلى تاريخ», defaulting to the last 30 days (real today, never `TODAY_ISO`). Each line shows date, receipt number, contract, client, unit, building, what it paid («دفعة حجز» / «المقدم» / «التأمين» / «القسط n» via `kindOf`), the method and the amount; dates and methods come back as API enums, so the screen maps them through `PAYMENT_METHOD_FROM_API`.
- Cards are `summary.collected`, `summary.net` (with the cancelled figure as its hint), `summary.receipts` and the daily average over `summary.days`. The bar chart covers the period's last 14 days (or all of them when shorter, zero days included, from `by_day`), the donut is `by_method`. A footnote appears when lines ≠ receipts. When `cancelled_payments` is non-empty, a second table lists them (payment and cancellation dates, receipt, contract, client, unit, method, amount and `cancel_reason`) — reported, never part of the collection.
- Both tabs share the API-error banner with «إعادة المحاولة» and a real-today `toISO(new Date())`; their export/print use `ReportActions` with the period/building details.
- The only report tab still on demo data is «عقود الإيجار» (in this screen); the units report's «حالة الوحدات» tab is wired too — see below.
- Requests send `Accept-Language: ar`, so API messages and validation errors come back in Arabic.
- Login is **single-session** server-side: every successful login revokes the user's previous tokens, so logging in elsewhere signs this browser out.
- Demo seed data is still used by contract-end, renewals, the «عقود الإيجار» report tab and the six per-status unit tabs (plus the other not-yet-linked screens).
- The API allows CORS from any origin in development via `backend/config/cors.php`.

## Loading speed

Data loading is server-side on the eight collection pages, the wired reports and the header bell, so it is worth keeping the request count and the PHP cost down:

- **Same-origin API in dev.** `vite.config.ts` proxies `/api` to `http://127.0.0.1:8000` (`VITE_API_PROXY` overrides the target), so the front-end calls `/api/v1/...` and the browser sends no CORS preflight. A build still talks to `http://localhost:8000/api/v1` unless `VITE_API_URL` is set. The backend must run through `backend/scripts/serve.sh` (opcache + workers) — see `backend/AGENTS.md`.
- **One request per GET.** `request()` in `src/lib/api.ts` shares an in-flight promise for identical GETs. React StrictMode mounts effects twice in dev, so without this every list was fetched twice.
- **Pickers load on demand.** The units page fetches the building list it needs for its filter; the reservations page only loads clients/units/buildings when a drawer opens, not when the page mounts.
- **Paged lists in parallel.** `fetchAllBuildings` / `fetchAllClients` / `fetchReservableUnits` read page 1 to learn `last_page`, then fetch the remaining pages together instead of one round trip each.
- Dev-mode page *boot* (~0.6–1s) is Vite compiling/serving the module graph and is unrelated to the API; hash navigation between pages afterwards costs one ~0.1s request.

## Styling

This project uses **Tailwind CSS v4** through the `@tailwindcss/vite` plugin configured in `vite.config.ts`. `src/index.css` imports Tailwind with `@import 'tailwindcss';`. Use Tailwind utility classes directly in JSX and put global CSS or Tailwind v4 theme customization in `src/index.css`. This scaffold does not need a Tailwind config file or PostCSS config.

`src/main.tsx` imports `src/index.css`, so global font wiring belongs in `src/index.css`. Keep CSS `@import` statements first, then add any `@font-face` rules and font-family defaults there.

Tailwind emits utility classes in `@layer utilities`, and CSS outside any cascade layer overrides every layer regardless of specificity. Put global element styles, such as resets and defaults for `body`, headings, `button`, or `input`, inside `@layer base { ... }` so utility classes on those elements still apply. Tailwind's Preflight already applies `box-sizing: border-box`, removes default margins, and sets `font: inherit` on form controls, so do not repeat those rules.

## Design System — نظام الحركة العقارية

Arabic RTL real estate management desktop app. `<html lang="ar" dir="rtl">` (lang comes from `.figma/make/site.json`, `dir` is set in `index.html`). Use logical properties/utilities (`ms-*`, `pe-*`, `start-*`, `text-start`) so layouts stay RTL-correct. Do not build showcase/demo/style-guide pages.

- **Font**: Cairo 400/600/700/800 via the Google Fonts `@import` at the top of `src/index.css` (`display=swap`), set as Tailwind `--font-sans`.
- **Tokens**: raw CSS variables live in `:root` / `.dark` in `src/index.css` (`--bg`, `--primary`, `--text`, `--glass*`, `--r-card`, `--r-ctl`, ...). They are mapped to Tailwind utilities through `@theme inline`: colors `bg`, `fg`, `fg-2`, `fg-3`, `primary`, `primary-2`, `primary-soft`, `hairline`, `success(-soft)`, `danger(-soft)`, `warning(-soft)`, `neutral(-soft)`; radii `rounded-card`, `rounded-ctl`; shadows `shadow-soft`, `shadow-raised`; easing `ease-spring`. Prefer these over raw hex values.
- **Dark mode**: class-based (`<html class="dark">`, `dark:` variant). Use `useTheme()` from `src/lib/theme.ts`; the toggle belongs only in the app header. `index.html` restores the saved theme before first paint.
- **Typography**: `h1`, `h2`, `label`, `th`, `td`, and `body` are styled globally. Classes: `t-page` 28/800, `t-section` 18/700, `t-body` 14/400, `t-label` 13/600, `t-caption` 12/400 (`--text-3`), `t-th` 13/700, `t-td` 14/400, `t-kpi` 26/800. In JSX prefer `<Text variant="...">`.
- **Surfaces**: `.glass` (blur 14), `.glass-strong` (blur 18), `.glass-float` (blur 20 + lifted shadow), `.backdrop` for overlays (blur 4px max). Component: `<GlassCard variant>`.
- **Motion** (transform/opacity only): `.fade`, `.pop`, `.rise-in`, `.drawer-in` (slides from the left, inline-end in RTL), `.toast-in`, `.skeleton`, `.spinner`. Reduced motion disables all animation/transitions and hides `.mesh`.
- **Performance**: `index.html` adds `low-perf` to `<html>` when `hardwareConcurrency <= 4` or `deviceMemory <= 4`; glass then drops `backdrop-filter` and `.mesh` is hidden. Keep `<MeshBackground />` to exactly two blobs and render page content above it (`relative z-[1]`).
- **Components** (`@/components/ui`): `MeshBackground`, `GlassCard`, `Text`, `Button` (`primary | danger | success | glass | ghost`, sizes `sm | md | lg`, `loading`, `iconStart`/`iconEnd`), `Input` / `Select` / `Textarea` (`label`, `hint`, `error` → `.field.err`), `FieldShell`, `Badge` (`tone`), `StatusBadge` (maps Arabic statuses via `STATUS_TONE`: green نشط/مدفوع/مكتمل/متاحة · yellow مسودة/محجوزة/جزئي · red ملغي/متأخر/غير قابلة للبيع · indigo مباعة/مرحل/محوّل لعقد · sky مؤجرة/مجدد · neutral منتهي/معلق/مرتجع/مرتجعة), `Skeleton`. Use `cn()` from `src/lib/cn.ts` to merge classes.

## New UI (update v5) — what is different from the previous build

- **Login = the API session (no local accounts).** `src/lib/auth.tsx` is now a thin wrapper over the Sanctum token: `login(identifier, password)` → `POST /auth/login`, `/auth/me` restores the user on reload (`ready` keeps the login page from flashing), `logout()` → `POST /auth/logout` then clears the token. `App.tsx` gates the app: `AppProvider → AuthProvider → ToastProvider → Gate → DataProvider → RecordHostProvider → Shell`. There is no registration, no password recovery and no guest bypass in the UI — users, roles and permissions come from the server.
- **One way to lose the session.** The token disappearing (`clearToken()` on a 401/419 in any screen, a second login elsewhere revoking it, or «خروج») signs the app out through the token event, and the login screen shows «انتهت الجلسة، سجّل الدخول من جديد.» unless the sign-out was intentional. Screens no longer render an `ApiLoginCard`; that component was removed.
- **Kit.** `DataTable` keeps the server-mode props (`serverSearch` / `serverSort` / `serverPagination`) that the API pages need, plus the new `printOnly` column flag (kept in print/export, hidden on screen). `src/kit/codes.ts`, `src/lib/codes.ts` and `src/components/BrandLogo.tsx` are new.
- **Screens.** New `screens/reports/ReportIncome.tsx` and `ReportStatements.tsx`; `Settings`, `GlobalSearch`, `Contracts`, `Receipts`, `RentDue`, `ContractEnd`, reports and `records` were restyled.
- **Data model (demo screens).** `Building` gained `address` + `types` (multi-select), sale terms carry an optional `discount` / `discountReason`, and a reservation's `expiryDate` may be empty. The API-era fields (`apiId`, `kind`, `activities`, `hasBasement`, `unitsCount`) are **optional** on `Building` and are set by `buildingFromApi()`; only the buildings page reads them.
- Kept from the API work: `src/lib/api.ts`, the eight server-driven screens, the `/api` Vite proxy and the `Loading speed` section above.
